# GlobeTrotter — Frontend Screen Specification

**Document:** Frontend Screen-by-Screen Specification  
**Version:** 1.0  
**Source:** Team Excalidraw mockup + GlobeTrotter project brief  
**Scope:** Frontend structure, screens, components, interactions, navigation and UI states  
**Screens:** 12

---

## 1. Purpose

This document defines the frontend structure of the GlobeTrotter application.

It is intended to act as the team's frontend blueprint before implementation. It specifies:

- What screens exist
- What each screen is responsible for
- Major and minor UI elements
- User actions
- Navigation between screens
- Search, filter, grouping and sorting behavior
- Important UI states
- Reusable components
- Areas requiring clarification before implementation

This document describes **frontend behavior and structure**. Database schema and backend implementation are outside the current scope.

---

# 3. Global Frontend Requirements

These elements should remain consistent across the application.

## 3.1 Global Header

Where applicable, the header should contain:

- GlobeTrotter branding/logo
- Navigation or menu control
- User/profile access
- Page title where appropriate
- Logout/access control where appropriate

## 3.2 Global Search Controls

Several screens in the mockup use the same controls:

- Search bar
- Group By
- Filter
- Sort By

These should be implemented as reusable UI components so that behavior and appearance remain consistent.

## 3.3 Common UI States

Every data-driven screen should account for:

- Loading state
- Empty state
- Successful data state
- Error state
- No search results
- Validation/error messages
- Confirmation state for destructive actions

## 3.4 Responsive Layout

The frontend should remain usable on:

- Desktop
- Laptop
- Tablet
- Mobile

The mockup is desktop-oriented, so responsive behavior should be treated as an implementation requirement rather than assumed to be represented visually in the mockup.

# 4. Screen 1 — Login

## Purpose

Authenticate an existing GlobeTrotter user and provide access to the main application.

## Major UI Elements

1. GlobeTrotter branding
2. Login card/container
3. User/profile image or visual placeholder
4. Username input
5. Password input
6. Login button

## Minor UI Elements

- Input labels/placeholders
- Password visibility control
- Required-field indicators
- Validation messages
- Authentication error message
- Loading state on Login button
- Link/action to Registration
- Link/action for password recovery if included

## User Actions

### Login

```text
Enter credentials
      ↓
Validate fields
      ↓
Submit
      ↓
Authentication
      ↓
Success → Screen 3
Failure → Display error
```

## Validation

- Username must not be empty
- Password must not be empty
- Invalid credentials must produce a clear error state

## Navigation

- Successful Login → **Screen 3: Main Landing Page**
- Registration → **Screen 2**
- Forgot Password → recovery flow if implemented

# 8. Screen 5 — Build Itinerary

## Purpose

Construct the actual trip itinerary from multiple sections/stops.

This is one of the application's primary working screens.

## Major UI Structure

Each itinerary section contains:

- Section title/name
- Section information/description
- Date range
- Section budget
- Activities/content associated with the section

### Add Another Section

A dedicated action allows the user to add additional sections/stops.

## Example Structure

```text
Trip
 ├── Section 1
 │    ├── Destination
 │    ├── Date Range
 │    ├── Activities
 │    └── Budget
 │
 ├── Section 2
 │    ├── Destination
 │    ├── Date Range
 │    ├── Activities
 │    └── Budget
 │
 └── Section 3
      ├── Destination
      ├── Date Range
      ├── Activities
      └── Budget
```

## Major Functions

- Add section
- Select destination
- Set section date range
- Add activity
- Remove activity
- Edit section
- Remove section
- Set/update section budget
- Reorder sections
- Save/update itinerary

## Search Integration

Selecting a destination/activity should open or invoke:

→ **Screen 8: Activity / City Search**

After selection:

→ Return to **Screen 5**

## Minor UI Elements

- Expand/collapse section
- Edit button
- Delete/remove button
- Date picker
- Budget input
- Activity cards
- Destination image
- Save/continue action
- Unsaved-change indication if required

## Important Design Principle

Screen 5 is the **editing/builder view**.

Screen 9 is the **view/read/review view**.

These two should not be treated as the same screen.

# 18. UI State Requirements

For each major data-driven component, account for:

### Loading

Show a loading indicator/skeleton while information is being retrieved.

### Empty

Example:

```text
No upcoming trips yet.
Plan your first trip.
[Plan a Trip]
```

### Error

Show a readable error and provide a retry action where appropriate.

### Search Empty

```text
No results found.
Try a different search term or filter.
```

### Form Validation

Show validation close to the relevant field.

### Confirmation

For destructive actions such as deleting a trip, ask for confirmation.

# 21. Mockup Clarifications / Open Decisions

These should be resolved by the team before frontend implementation.

## 21.1 Create Trip — Duplicate Start Date

The mockup shows two fields labelled "Start Date".

**Action:** Confirm the intended field before implementation.

## 21.2 Search — One Screen or Two

The mockup labels Screen 8 as:

**Activity Search Pages / City Search Page**

**Recommendation:** Keep a common search/selection component and allow it to operate in City or Activity mode.

## 21.3 Itinerary Sections

The mockup uses "Section" rather than explicitly calling each section a "Stop" or "City".

**Action:** Team should confirm terminology and behavior.

## 21.4 Community Functionality

The mockup confirms experience sharing, search, filtering and sorting, but does not fully define:

- Comments
- Likes
- Following
- Post creation workflow
- Post editing/deletion

These should be considered optional until confirmed.

## 21.5 Admin

Admin functionality should remain separate from the normal user journey and be role-protected.

---

# 22. Definition of Frontend Completion

The frontend structure can be considered complete when:

- All 12 mockup screens are represented.
- Every major button has a defined action.
- Navigation between screens is defined.
- Core trip creation flow works conceptually from Login → Home → Create Trip → Build Itinerary → Search → Itinerary.
- Search/filter/sort/group controls have defined purposes.
- Loading, empty, error and validation states are accounted for.
- Reusable components are identified.
- Mockup ambiguities are resolved before implementation.
- Admin functionality is isolated from normal users.
- The frontend specification can be handed to the implementation team without requiring them to infer the intended screen flow.
